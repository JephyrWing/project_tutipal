## 자료 구성과 사용

자료 12개, 질문 24개(근거 있음 20/없음 4), 전처리 경계 표본 12개다. 분수 덧셈/곱셈, 현재완료/단순과거, for/while, 광합성/호흡, 빗변/넓이처럼 단어가 비슷해도 답이 다른 정상 자료를 함께 넣었다. 가상 표와 자료 속 지시문도 포함한다. 틀린 사실을 정답 자료로 심지 않았다.

각 질문에는 고정 `query_id`, 관련 `doc_id`, 헷갈리기 쉬운 비관련 `hard_negative_doc_ids`, 참고 답과 실제 원문 근거 문자열이 있다. 관련 자료가 두 개인 Q06은 두 근거를 모두 확인한다. 질문의 근거 존재 여부를 모델의 일반 지식 보유 여부와 혼동하지 않는다.

자료의 `page: 1`은 논리적인 합성 문서 페이지다. PDF 추출을 검사했다는 뜻이 아니다. 후속 평가에서 원본 `doc_id`·파일명·페이지·근거 문자열과 실제 chunk ID/offset의 대응을 보존한다. 청킹을 바꾸어도 원본 정답을 조용히 바꾸지 않는다.

평가 입력은 질문 텍스트와 선택한 자료 본문뿐이다. `reference_answer`, `evidence`, 관련/비관련 ID, `answerable`은 채점자가 보관하고 검색·생성 입력에 넣지 않는다. 정답 누출을 금지한다. D12의 지시문은 데이터로 취급한다. 모든 자료는 같은 가상 수업 범위로, 실제 권한 거절을 이 세트만으로 통과시킬 수 없다.

개발·전처리 비교용으로 공개된 세트이며 독립 holdout은 없다. 이 세트로 튜닝한 뒤 같은 점수를 일반화 성능으로 보고하지 않는다. 실제 자료와 별도 보류 평가 세트가 필요하다.

## 현재 코드에서 확인한 기준

다음 표의 최초 기준은 2026-11-24다. PT-86 PR #57/V20 이후에도 기본값은 `char800-v1`(800/100), 리랭커 OFF, 코사인 0.5, 1024차원이다. V20은 `material_chunks.chunker`에 청커 출처를 기록하며, 임베딩 출처는 기존 `embedding_model` 태그로 구분한다. V20이 NFC/B1 전처리 버전까지 자동 식별하는 것은 아니다.

이 세트는 임베딩·전처리 비교용 공개 개발 세트다. `tutipal_back/src/ragEval/`의 PT-86 봉인 질의는 청킹·리랭커 비교용이므로 세트·점수·실행 수를 섞지 않는다.

| 항목 | 현재 동작과 근거 |
| --- | --- |
| 문서 청킹 | `Chunker.split`: CRLF→LF, 연속 공백/탭→한 칸, 3개 이상 LF→2개, 앞뒤 strip. 문단을 글자 수 기준으로 분할하고 20자 미만 조각 제외 |
| 크기/배치 | `MaterialService`: size 800, overlap 100, 한 번에 32조각. Java 문자열 길이 기준이며 모델 token 수가 아님. overlap/개행 때문에 최종 조각 길이가 정확히 800이라고 단정하지 않음 |
| 검색 질의 | `RagSearchService`: `query.strip()` 후 임베딩. 문서와 동일한 정규화 규칙은 아님 |
| Python 입력 | `EmbedRequest`: 한 요청 1~64개, 문자열 1~4000 code point. `ollama_client`는 받은 문자열을 모델에 그대로 보냄 |
| 벡터 | Python 설정과 Spring 계약은 1024차원. `provider:model:dimension` 출처를 반환하고 같은 수업·같은 출처로 검색. 코사인 0.5 이상, 최대 3개. V20 청커 출처와 별개로 NFC/B1 정규화 버전은 현 임베딩 출처 태그에 포함되지 않음 |

현재 공백 축약은 코드 들여쓰기·문자열 내부 공백을 바꿀 수 있다. 이 문서는 그 동작을 승인하거나 수정하지 않는다. P03을 PT-86 청킹 대조에 사용한다.

## 전처리 비교 조건 (평가 당시 제안, 최종 선택은 아래 요약)

원본은 읽기 전용으로 보존하고 변환 결과를 별도 보관한다. 결과마다 `preprocessing_version`, 문서/질의 프로필, 입력·출력 해시, 원문 근거 대응, 변경 이유를 기록한다. 같은 모델명/차원이어도 서로 다른 문서 전처리 결과를 하나의 비교 인덱스에 섞지 않는다.

| 조건 | 문서 | 질의 | 판단 목적 |
| --- | --- | --- | --- |
| B0 현재 코드 | 실제 Spring Chunker 결과 고정 | 현재 strip | 현재 동작 기준선. Python으로 흉내 낸 결과를 실제 Java 결과라고 하지 않음 |
| B1 보존형 정규화 | NFC, CRLF/단독CR→LF. 코드·표·수식·문단과 내부 공백 유지. 본문 자체를 strip하지 않음 | NFC+개행 정리 후 바깥 공백 제거, 내부 공백 유지 | 조합형 한글·개행 차이를 줄이면서 의미·구조 보존 |
| B2 일반 문장만 공백 정리 | B1에 추가해 일반 문장 영역의 공백/탭만 축약. 코드·표는 제외. 영역 분류 방식까지 고정해야 실행 가능 | 일반 자연어 질의만 같은 방식으로 정리. 코드 질의는 B1 | 무조건 공백 삭제와 구분하여 효과 평가 |
| B3 모델별 권장 접두문 | 선택 모델 공식 model card의 document 형식 확인 후 적용 | 같은 모델의 query 형식 적용 | 모델·revision·원문 URL·접두문을 확정한 뒤 별도 실행. 임의 query:/passage:나 다른 모델 규칙을 복사하지 않음 |

B1/B2는 비교 후보이며 제품 코드에 구현하지 않았다. B2 영역 분류와 B3 모델별 형식은 아직 미정이다. B0/B1/B2/B3를 한 번에 바꾸지 않고 문서/질의별 효과도 분리한다. NFKC, 영문 소문자화, 숫자·구두점·단위·부정어 삭제, OCR 오인식 자동 교정, 자료 지시문 실행은 기본 제안에서 제외한다.

### 길이·빈 입력·배치

- 빈 문서/공백만 문서는 제외 사유를 남긴다. 공백만 질의는 모델 호출 전에 거절하는 방향으로 제안한다. 현 Pydantic 길이 검사가 모든 whitespace 입력을 막는다는 뜻이 아니다.
- 원본 긴 문서는 PT-86이 정할 구조 보존 청킹으로 처리한다. 뒤의 근거를 잃는 조용한 앞 4000자 절삭을 하지 않는다. P12로 문서 끝 근거 보존을 비교한다.
- 임베딩 실제 전송 텍스트는 접두문을 포함해 Python 4000 code point 및 해당 모델 token 한도를 모두 만족해야 한다. Spring 실제 경로가 Java 길이 제한을 추가하면 UTF-16 단위도 확인한다. 둘을 같은 단위로 취급하지 않는다(P07~09).
- 비교 실행 초기에는 현재 Spring의 32개 배치 크기를 고정하고 최대64개 계약을 넘기지 않는다. 배치/정규화/모델 변경의 속도 효과를 섞지 않는다. 초과는 명시 거절 또는 PT-86에서 정한 재분할이며 제공자의 조용한 truncation 여부도 기록한다.
- 길이가 다른 코드·수식·표를 일반 문장과 섞어 평균 하나로 숨기지 않는다. 실제 PDF/OCR 입력 품질과 짧은 문서 제외 정책은 후속 검증이다.

### 벡터 변경·재인덱싱

768차원 embeddinggemma를 현 1024차원 DB에 이름만 교체하거나 zero padding하지 않는다. 모델/차원 변경은 별도 데이터 경계·migration·재인덱싱 검증이 필요하다. 문서 전처리 변경도 기존 출처 태그가 같게 남을 수 있으므로 격리 인덱스/manifest로 버전을 구분하고 PT-99와 공개·전환·복구 기준을 맞춘다. 현 DB나 태그 형식은 이 문서로 바꾸지 않는다.

## 실행·측정 계획: 결과 아님

1. 원본·질문·정답 라벨을 고정하고 데이터 해시를 기록한다. 같은 자료에 같은 청킹 조건을 사용한다. 청킹 비교는 별도 단계다.
2. 모델/제공자/revision/digest/차원·token 한도·접두문·전처리 버전·batch·하드웨어를 고정해 기록한다.
3. 임베딩 품질은 원본 자료 수준 Hit@1, Recall@3, 첫 관련 자료의 MRR@3을 근거 있는 20질의에 계산한다. Recall@3은 질문별 관련 doc 중 상위3에 포함된 비율의 평균이다. 여러 chunk가 같은 doc이면 doc_id를 중복 제거하되 원본 순서를 유지한다.
4. 근거 없는 4질의는 별도 집계한다. 현재0.5 기준에서 무관자료가 노출되는 비율/질문 ID를 기록한다. 이 개발세트만으로 threshold를 튜닝하고 성능을 확정하지 않는다.
5. 대화 평가에는 현재 개인채팅 지시문 버전과 동일 질문을 사용한다. RAG 생성 비교는 별도 조건으로 동일 근거를 고정해 제공한다. 핵심 사실, 근거 일치, 수식/코드/단위, 근거 없음 인정, 지시문 무시를 사람이 항목별 검토한다. 참고 답과 문자열 일치를 정답 기준으로 삼지 않는다. Q21~24에서 일반 답변을 하는 현재 제품 동작과 자료 근거가 있다는 허위 주장을 구분한다.
6. 단독 요청을 cold/warm 각 3회 측정하는 것을 다음 예비실행안으로 제안한다. 첫delta·완료·응답 글자/실제 token(제공 시)·RAM·에러/중지/제한을 분리한다. cold는 모델 비상주 여부를 확인하고 실행 순서를 기록한다. 3회는 통계적 충분성/SLA가 아니다.

출처 최대3개, 다른 수업/출처 혼합 금지 등 확정 계약과 점수 목표를 구분한다. 전체 정확도/속도 합격선·최종 모델·장시간 부하 조건은 측정 후 근거와 함께 Jira 결정으로 남긴다. 임의의 90%/7초 같은 목표를 승인된 기준으로 추가하지 않는다.

실행 기록에는 `run_id`, 데이터/스크립트 SHA256, 최종 Git SHA, UTC/KST 시작·종료, 환경, 명령·종료코드, 모델 metadata, 전처리 프로필, 실제 수집·실행·성공·실패·오류·skip, 질문별 순위/출처/점수/지연과 미검증 범위를 남긴다. 초과/실패 응답을 완료 시간 평균에 섞거나 이전 결과를 새 버전에 승계하지 않는다.
