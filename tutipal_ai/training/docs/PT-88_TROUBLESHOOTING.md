# PT-88 채점 학습 데이터 v3 — 트러블 슈팅

## 1. 정답 비율이 목표를 넘음 (0.50, 목표 0.30–0.45)

**증상**: `augment_tricks`의 `composition.label_true_share`가 0.50(정답 734 / 오답 734). v2는 0.411. `trainmix`(코딩 0.830, 꼼수 0.149)와 dev `leakcheck`(실패 0)는 통과.

**원인**: v3 라벨 규칙의 채점자 불일치 제외(`MOHLER_DISAGREE_GAP = 3`)가 **오답 후보에만** 적용된다. 두 채점자 점수 차(5점 척도로 맞춘 뒤)가 3 이상인 Mohler 오답 203행이 빠지면서 오답 쪽만 줄었다.

점수 차별 제외 수(정규화 후, 오답 후보):

| 점수 차 | 3.0 | 3.25 | 3.5 | 3.75 | 4.0 | 4.5 | 4.75 | 5.0 |
|---|---|---|---|---|---|---|---|---|
| 행 수 | 105 | 5 | 11 | 16 | 55 | 3 | 1 | 7 |

**검토한 선택지**

- A. 0.50 그대로 쓴다.
- B. 계획서 가정대로 기준을 3.5로 올린다. 돌아오는 후보는 110행(3.0·3.25)뿐이고 문항당 상한(Mohler 12행) 때문에 실제로 남는 건 더 적다. 0.45 아래로 내려가려면 오답이 약 160행 더 필요해 목표에 닿기 어렵다. 새 후보는 번역·작성이 없어 "조립만 다시"가 아니라 GPU 생성(약 10분)이 다시 필요하다.

**결정 (2026-11-25, PM)**: A. 정답·오답이 반반이라 한쪽으로 크게 기울지 않았고, 학습 게이트는 모두 통과했다. 0.45는 `trainmix` 게이트가 아닌 README 구성 목표다.

**다음에 할 일**: 실제 수업처럼 오답이 많은 분포가 필요하면, 불일치 제외를 정답 후보에도 대칭으로 적용하거나 `clean_grading_c`에 라벨별 상한을 두는 방안을 검토한다. 학습 뒤 채점 결과가 "후하게 맞다고 하는" 쪽으로 기울면 이 항목부터 본다.

## 2. 생성 중 메모리 부족으로 강제 종료

**증상**: 번역 2,480/2,672행에서 생성 프로세스가 끊겼다. Claude Code가 "system is running low on memory"로 백그라운드 작업을 종료했다. 같은 날 오전에는 Codex 리뷰가 같은 이유로 판정 없이 끊겼다.

**원인**: RAM 15.4GB 노트북에서 커밋 메모리가 한도(약 33.7GB)에 닿았다. 프로세스별 커밋은 다음과 같았다.
- Ollama `llama-server`(translategemma·gemma3 4B): 10–13GB. RAM 사용은 약 5GB인데 커밋은 두 배 이상 잡는다.
- Claude Code 세션 11–13개: 약 5–6GB
- MySQL: 약 3GB
- Edge·ChatGPT·Notion·Discord: 약 4GB
- 병렬 세션의 Gradle 데몬: 약 1GB

**조치**
- 캐시가 행 단위로 바로 저장돼서 같은 명령으로 이어 돌렸다(번역 남은 약 190행만 다시 함).
- 다시 돌리기 전에 ChatGPT·Notion·Discord를 닫았다(커밋 33.1 → 30.1GB). 병렬 세션(PT-87, PT-106)에는 생성이 끝날 때까지 gradle·npm·pytest와 Ollama 사용을 미루게 했다.
- 이어 돌리기를 보강했다. Ollama 예외(`URLError`·`TimeoutError`·`HTTPError` 등 `TRANSIENT_ERRORS`)로 기록된 행은 다시 시도한다. 전에는 예외가 오류로 캐시돼서 이어 돌려도 영원히 건너뛰었다.
- Codex 리뷰는 모델이 내려간 시점(커밋 약 20GB)에 돌렸다.

**다음에 할 일**: GPU 생성은 다른 무거운 작업(gradle, Docker, 다른 Ollama 모델)과 겹치지 않게 돌린다. 시작 전에 `Get-Counter '\Memory\Committed Bytes','\Memory\Commit Limit'`로 여유를 확인하고(작성 모델이 올라가면 약 13GB가 더 잡힌다), MySQL처럼 안 쓰는 서비스는 끈다.

## 3. 번역 검사 오탐 — SAF 실패율 54.6%

**증상**: v2 번역 캐시에 검사를 돌렸을 때 SAF 행의 54.6%가 실패했다(Mohler 7.3%). 문장 단위로는 20.6%.

**원인**: 숫자 규칙의 오탐과, SAF 문항·모범 답안을 여러 행이 함께 쓰는 구조. 문장 하나가 걸리면 수십 행이 같이 빠진다.
- 목록 번호: 영어는 `1. … 2. …`를 한 줄에 이어 쓰고 번역은 줄을 나눈다. 줄 맨 앞 번호만 빼서 영어 쪽에만 수가 남았다.
- 붙임표 낱말: two-way→양방향, half-duplex→반이중
- 한국어 낱말 속 수: bi-dimensional→2차원
- 유럽식 소수점: 0,6→0.6 (SAF에 독일 학생 답안이 섞여 있음)
- `give 1 advantage`→`장점을 각각`

**조치**: 위 다섯 가지만 좁게 빼고(`CHECK_VERSION` pt88-3), 진짜 오류(`0.  5 P`, 소수점 자리 바뀜)는 계속 걸리는지 테스트로 고정했다. 처음 수정은 `(phase 5)`·`{0,1,2}`까지 빼서 오탐이 1/17에서 4/17로 늘었고, 범위를 다시 좁혔다. 결과: 전체 실패율 16.0% → 14.2%, 1차 검수 30행 기준 재현율 8/13, 오탐 1/17(변화 없음).

**남은 것**: 행 단위 SAF 실패율은 48%로 여전히 높다. 상당수는 용어집 없이 번역한 예전 캐시의 unicast·free·memory 오역이고, v3에서는 용어집을 넣어 다시 번역했다.

## 4. 검사 규칙 버전이 번역 캐시 키에 들어 있음 (알려진 한계)

**증상**: 검사 규칙을 고치면 `CHECK_VERSION`을 올려야 하는데, 이 값이 번역 캐시 키(`#p=`)에 들어 있어서 올리면 모든 행을 다시 번역한다(약 25–30분).

**조치**: Codex 2라운드의 규칙 추가(5자 이하 약어, `just + 수`)는 v3 생성 도중이라 버전을 올리지 않았다. 조립 단계가 캐시 번역을 지금 규칙으로 다시 검사하므로 규칙은 적용된다. 실측으로 v3 캐시 2,272행 중 새 규칙에 처음 걸리는 행은 0이었다.

**다음에 할 일**: 다음 규칙 변경 때 키에서 `CHECK_VERSION`을 빼고, 규칙이 바뀌면 `trans_check` 오류로 저장된 행만 다시 번역하게 바꾼다(키가 바뀌므로 그때 한 번은 전부 다시 번역).

## 5. 남은 리뷰 지적 (Codex 3라운드, 반박)

- 번역문에 원문에 없는 한글 수사가 **더해진** 경우(`3 hosts`→`세 호스트 네 개`)를 잡지 못한다. 한국어 수사는 영어 → 한국어 방향만 본다. `both`→`두 경우 모두`, `second`→`두 번째`, 관사 `a`→`한` 같은 정상 번역이 오탐이 되기 때문이다. 계획서 7번("숫자 집합 일치")과는 어긋난다. 고친다면 "3 이상의 수사 + 단위"로 좁혀 추가한다.

## 6. 새 용어집이 기존 테스트의 합성 문항에 걸림

**증상**: 기존 파이프라인 테스트 30여 개가 실패했다. 합성 Mohler 문항(`... inserts a new element.`)과 SAF 문항에 `element`·`frame`이 들어 있는데 가짜 번역에는 `요소`·`프레임`이 없었고, 가짜 오답 reason(`핵심 개념이 누락되어 있다.`)은 새 `expl:vague_missing`에 걸렸다. 번역 캐시 키에 그 행 원문의 용어집 항목이 들어가므로, 원문 없이 키를 만들던 테스트 3개도 키가 맞지 않았다.

**조치**(강지 판정 1): 영어 입력·기대 개수·규칙 이름은 그대로 두고 가짜 모델 출력만 고쳤다(가짜 번역에 v4 용어의 첫 허용형을 붙이고, 가짜 오답 reason에 모범 답안 내용을 넣음). 원문 없이 키를 만들던 3곳은 원문이 든 항목으로 키를 만든다. v4 규칙에 걸려 빠지는 행이 남도록 v2 통합 테스트에 vague reason 행 1개를 두고 `expl:vague_missing`으로 빠지는지 확인한다.

## 7. `baud` 용어가 예전 테스트의 `only` 사유를 가림

**증상**: `a full bit per baud instead of only 0.5` → `0.5보다 훨씬 더 많은 정보`는 v3에서 `only`로 거절됐는데, 용어집을 먼저 보니 `glossary:baud`가 먼저 나왔다.

**조치**: v4 용어(forms 항목)와 단위 규칙을 예전 규칙(처음 5개 용어 → 약어 → 수 → 비교 → 한정 → 부정) 뒤에 본다. 거절되는 칸은 같고 사유 이름만 예전 그대로라 v3와 탈락 사유 통계를 비교할 수 있다.

## 8. 붙임표 표기가 일반 구문에 맞음 (`in-order` → `in order to`)

**증상**: inorder의 표기 `in-order`를 공백·붙임표 모두로 맞추니 SAF·과학 원문의 `in order to`·`in order`가 inorder로 잡혀 `중위`를 요구했다.

**조치**: 붙임표로 쓴 표기는 붙임표만, 공백으로 쓴 표기(`base case`)는 공백·붙임표 모두 맞게 했다. 그래도 SAF의 `in-order byte stream`·`in-order delivery`(순서 보장 전달)가 남아 inorder 표기에서 `in-order`를 뺐다(`pre-order`·`post-order`는 유지). v3 원문 기준 inorder로 잡히는 텍스트가 SAF 9개 → 0개, Mohler 23개 → 6개(모두 진짜 inorder)로 줄었다. Mohler 원문 1곳(`in-order, post-order, and pre-order traversal`)의 `in-order`는 놓친다.

## 9. 설명 검사 오탐 — `기억하시면`, 괄호 속 영어 풀이

**증상**: v3 train_aug 비꼼수 1,249행에 v4 설명 규칙을 돌리니 `expl:glossary:memory` 8행이 모두 feedback의 `기억하시면`(remember)이었고, `expl:foreign` 23행 중 15행은 `정적(static)`·`값(value)`·`LIFO(Last-In, First-Out)` 같은 괄호 속 영어 풀이였다.

**조치**: 설명 속 금지형은 바로 뒤에 동사를 만드는 말(하·해·했·되 등)이 오면 보지 않는다(모든 용어에 같게, 강지 판정 3). 한국어 낱말·약어 바로 뒤 괄호 속 영어는 외국어 낱말로 보지 않는다. 결과: foreign 8행(모두 `pyeong`·`slovnost`·`idać` 같은 진짜 잔해), glossary:memory 0행, glossary:argument 0행(판정 3의 남은 리스크 실측 0).

## 10. 한계 — 자동으로 못 잡는 것

- **사실 오류**: 작성 모델이 언어·규칙에 관한 틀린 사실을 단정하는 것(E11.Q03.A12의 "값이 없으면 0으로 초기화")은 규칙으로 판단할 수 없다. 이 행은 kind=wrong에서 학생 주장을 맞다고 한 표현(`wrong_affirmed`)으로만 잡혔다. 프롬프트에 근거 없는 단정 금지를 넣었다.
- **중요도 판단**: 학생이 사소한 차이만 말했을 때 그것이 핵심이 아니라고 짚는지(E01.Q07.A19)는 규칙으로 판단할 수 없다. 프롬프트로만 막는다.
- **원문 오타·문체**: SAF 원문의 `inference`(interference 오타), 의역·문체 문제(SAF-61484f2a)는 못 잡는다. SAF 문항은 고정 번역 시트의 선택 항목으로 사람이 고칠 수 있다.
- **vague_missing은 낱말 겹침만 본다**: 모범 답안의 낱말을 하나라도 말하면 통과한다(동의어로만 말하면 오탐, 엉뚱한 맥락에서 같은 낱말을 쓰면 놓침). v3 데이터에서 Mohler 14행·SAF 9행·과학 41행이 걸렸고, 생성 때는 두 번 다시 써 보고 그래도 걸리면 뺀다.
- **과학(SciEntsBank) 250행은 사람 검수를 하지 않는다**: 검수 시트는 코딩 과목(Mohler·SAF, `--min-saf 8`로 SAF 8행 이상)만 뽑는다.
- **고정 번역 출처**: 실제 고정 번역 시트 67문항은 OpenAI Codex 초안 + 팀원 확인이다. Codex 출력물을 학습에 쓰는 것이 OpenAI 약관에 맞는지는 아직 검토하지 않았다(검토 필요).
- **붙임표 합성어**: `multi-dimensional`의 dimension처럼 붙임표로 붙은 용어는 검사하지 않는다(11절).
- 번역 캐시 키 공식 정리(`CHECK_VERSION`을 키에서 빼기)는 숙제로 남겼다(4절).

## 11. Round 1 — 팀원이 확인한 고정 번역 5건이 규칙에 걸림

**증상**: 최종 고정 번역 시트(67문항, OpenAI Codex 초안 + 팀원 확인)를 `--pin`으로 넣으니 SAF 5건으로 종료 코드 2:
`수신 확인 있는 비연결형`(confirmed connectionless 허용형 밖), `60-second observation time-frame`의 frame, `클록이 완벽한`(perfect
clock 어순), `factor of 10`→`10분의 1`(number), `instead of only 0.5`→`0.5비트 대신`(only, 고쳐도 다음에 baud `보(baud)`).

**조치**(강지 Round 1 결정 1, 고정값은 바꾸지 않음): 뜻을 옮긴 번역이 걸리면 규칙이 틀린 것으로 보고 규칙을 좁게 고쳤다(통과·탈락 짝 테스트).
- 허용형 추가: `수신 확인 있는 비연결형`, `클록이 완벽`·`클럭이 완벽`·`시계가 완벽`, `보(baud)`·`보당`·`보 당`. `확인된 비연결`·`완벽한 시간`은 계속 금지, `보` 한 글자는 쓰지 않음.
- 붙임표 합성어의 한 부분은 용어로 보지 않는다(앞뒤 `[\w-]`). **판정과 다르게 한 점**: 같은 고정 번역에 `the time frame`(띄어쓰기)도 있어, 판정의 "띄어쓰기는 매칭"을 따르면 사람 번역 `관찰 시간`이 계속 걸렸다. 그래서 frame 항목은 관용구 `time frame`/`time-frame`을 지우고 찾는다(다른 곳의 frame은 그대로 잡음). 원천 SAF에 `time frame` 76곳, `time-frame` 61곳.
- 수: 한국어 `N분의 1`의 1은 세지 않는다(`N분의 M` 일반은 그대로).
- 한정: `instead of only <수>`이고 한국어에 `대신`이 있을 때만 only를 요구하지 않는다. 고치기 전 측정: 원천에서 이 구문은 SAF 모범 답안 1개 원문(이 원문을 쓰는 행 134), Mohler 0. v3에서 이 구문 때문에 only로 빠진 행은 0(v3 메모 번역은 only 표현이 있었고, v4에서는 baud에 걸리던 원문).
- `load_pins`는 칸마다 걸린 규칙을 모두 알리고(`trans_check_all`), UTF-8이 아닌 시트·머리글만 있는 시트·고정값 속 `"}`·`{`도 종료 2로 알린다.
- note의 AI 이름에 Codex·OpenAI를 넣었고(실제 시트 by_ai `{Codex: 67}`), 사람 확인 표시는 사람 주체(팀원·사람·검수자·사용자·직접·본인·PM)와 함께 쓴 `확인` 또는 주체 없는 `확인함`만 센다(`AI가 확인함`·`계산으로 확인함`·`확인하지 않음`·`확인 X`는 아님). 주체 없는 `확인함`을 세는 것은 기존 테스트 계약이다.
- 설명 규칙 wrong_affirmed: `정확하다고 보기 어렵다`·`옳다고 볼 수 없다`·`맞는 설명이 아니다`처럼 긍정 낱말 뒤에 부정이 오면 인정으로 보지 않는다.
