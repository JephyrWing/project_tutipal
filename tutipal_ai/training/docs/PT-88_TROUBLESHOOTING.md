# PT-88 채점 학습 데이터 v3 — 트러블 슈팅

2026-11-25 v3 생성(`derived/grading_v3/`) 중 겪은 문제와 결정. 배경과 수용 기준은 `PT-88_context.md`, `PT-88_plan.md`.

## 1. 정답 비율이 목표를 넘음 (0.50, 목표 0.30–0.45)

**증상**: `augment_tricks`의 `composition.label_true_share`가 0.50(정답 734 / 오답 734). v2는 0.411. `trainmix`(코딩 0.830, 꼼수 0.149)와 dev `leakcheck`(실패 0)는 통과.

**원인**: v3 라벨 규칙의 채점자 불일치 제외(`MOHLER_DISAGREE_GAP = 3`)가 **오답 후보에만** 적용된다. 두 채점자 점수 차(5점 척도로 맞춘 뒤)가 3 이상인 Mohler 오답 203행이 빠지면서 오답 쪽만 줄었다.

점수 차별 제외 수(정규화 후, 오답 후보):

| 점수 차 | 3.0 | 3.25 | 3.5 | 3.75 | 4.0 | 4.5 | 4.75 | 5.0 |
|---|---|---|---|---|---|---|---|---|
| 행 수 | 105 | 5 | 11 | 16 | 55 | 3 | 1 | 7 |

**검토한 선택지**

- A. 0.50 그대로 쓴다.
- B. 계획서 가정대로 기준을 3.5로 올린다. 돌아오는 후보는 110행(3.0·3.25)뿐이고 문항당 상한(Mohler 12행) 때문에 실제로 남는 건 더 적다. 0.45 아래로 내려가려면 오답이 약 160행 더 필요해 목표에 닿기 어렵다. 새 후보는 번역·작성이 없어 "조립만 다시"가 아니라 GPU 생성(약 10분)이 다시 필요하다.

**결정 (2026-11-25, PM)**: A. 정답·오답이 반반이라 한쪽으로 크게 기울지 않았고, 학습 게이트는 모두 통과했다. 0.45는 `trainmix` 게이트가 아닌 README 구성 목표다.

**다음에 할 일**: 실제 수업처럼 오답이 많은 분포가 필요하면, 불일치 제외를 정답 후보에도 대칭으로 적용하거나 `clean_grading_c`에 라벨별 상한을 두는 방안을 검토한다. 학습 뒤 채점 결과가 "후하게 맞다고 하는" 쪽으로 기울면 이 항목부터 본다.

## 2. 생성 중 메모리 부족으로 강제 종료

**증상**: 번역 2,480/2,672행에서 생성 프로세스가 끊겼다. Claude Code가 "system is running low on memory"로 백그라운드 작업을 종료했다. 같은 날 오전에는 Codex 리뷰가 같은 이유로 판정 없이 끊겼다.

**원인**: RAM 15.4GB 노트북에서 커밋 메모리가 한도(약 33.7GB)에 닿았다. 프로세스별 커밋은 다음과 같았다.
- Ollama `llama-server`(translategemma·gemma3 4B): 10–13GB. RAM 사용은 약 5GB인데 커밋은 두 배 이상 잡는다.
- Claude Code 세션 11–13개: 약 5–6GB
- MySQL: 약 3GB
- Edge·ChatGPT·Notion·Discord: 약 4GB
- 병렬 세션의 Gradle 데몬: 약 1GB

**조치**
- 캐시가 행 단위로 바로 저장돼서 같은 명령으로 이어 돌렸다(번역 남은 약 190행만 다시 함).
- 다시 돌리기 전에 ChatGPT·Notion·Discord를 닫았다(커밋 33.1 → 30.1GB). 병렬 세션(PT-87, PT-106)에는 생성이 끝날 때까지 gradle·npm·pytest와 Ollama 사용을 미루게 했다.
- 이어 돌리기를 보강했다. Ollama 예외(`URLError`·`TimeoutError`·`HTTPError` 등 `TRANSIENT_ERRORS`)로 기록된 행은 다시 시도한다. 전에는 예외가 오류로 캐시돼서 이어 돌려도 영원히 건너뛰었다.
- Codex 리뷰는 모델이 내려간 시점(커밋 약 20GB)에 돌렸다.

**다음에 할 일**: GPU 생성은 다른 무거운 작업(gradle, Docker, 다른 Ollama 모델)과 겹치지 않게 돌린다. 시작 전에 `Get-Counter '\Memory\Committed Bytes','\Memory\Commit Limit'`로 여유를 확인하고(작성 모델이 올라가면 약 13GB가 더 잡힌다), MySQL처럼 안 쓰는 서비스는 끈다.

## 3. 번역 검사 오탐 — SAF 실패율 54.6%

**증상**: v2 번역 캐시에 검사를 돌렸을 때 SAF 행의 54.6%가 실패했다(Mohler 7.3%). 문장 단위로는 20.6%.

**원인**: 숫자 규칙의 오탐과, SAF 문항·모범 답안을 여러 행이 함께 쓰는 구조. 문장 하나가 걸리면 수십 행이 같이 빠진다.
- 목록 번호: 영어는 `1. … 2. …`를 한 줄에 이어 쓰고 번역은 줄을 나눈다. 줄 맨 앞 번호만 빼서 영어 쪽에만 수가 남았다.
- 붙임표 낱말: two-way→양방향, half-duplex→반이중
- 한국어 낱말 속 수: bi-dimensional→2차원
- 유럽식 소수점: 0,6→0.6 (SAF에 독일 학생 답안이 섞여 있음)
- `give 1 advantage`→`장점을 각각`

**조치**: 위 다섯 가지만 좁게 빼고(`CHECK_VERSION` pt88-3), 진짜 오류(`0.  5 P`, 소수점 자리 바뀜)는 계속 걸리는지 테스트로 고정했다. 처음 수정은 `(phase 5)`·`{0,1,2}`까지 빼서 오탐이 1/17에서 4/17로 늘었고, 범위를 다시 좁혔다. 결과: 전체 실패율 16.0% → 14.2%, 1차 검수 30행 기준 재현율 8/13, 오탐 1/17(변화 없음).

**남은 것**: 행 단위 SAF 실패율은 48%로 여전히 높다. 상당수는 용어집 없이 번역한 예전 캐시의 unicast·free·memory 오역이고, v3에서는 용어집을 넣어 다시 번역했다.

## 4. 검사 규칙 버전이 번역 캐시 키에 들어 있음 (알려진 한계)

**증상**: 검사 규칙을 고치면 `CHECK_VERSION`을 올려야 하는데, 이 값이 번역 캐시 키(`#p=`)에 들어 있어서 올리면 모든 행을 다시 번역한다(약 25–30분).

**조치**: Codex 2라운드의 규칙 추가(5자 이하 약어, `just + 수`)는 v3 생성 도중이라 버전을 올리지 않았다. 조립 단계가 캐시 번역을 지금 규칙으로 다시 검사하므로 규칙은 적용된다. 실측으로 v3 캐시 2,272행 중 새 규칙에 처음 걸리는 행은 0이었다.

**다음에 할 일**: 다음 규칙 변경 때 키에서 `CHECK_VERSION`을 빼고, 규칙이 바뀌면 `trans_check` 오류로 저장된 행만 다시 번역하게 바꾼다(키가 바뀌므로 그때 한 번은 전부 다시 번역).

## 5. 남은 리뷰 지적 (Codex 3라운드, 반박)

- 번역문에 원문에 없는 한글 수사가 **더해진** 경우(`3 hosts`→`세 호스트 네 개`)를 잡지 못한다. 한국어 수사는 영어 → 한국어 방향만 본다. `both`→`두 경우 모두`, `second`→`두 번째`, 관사 `a`→`한` 같은 정상 번역이 오탐이 되기 때문이다. 계획서 7번("숫자 집합 일치")과는 어긋난다. 고친다면 "3 이상의 수사 + 단위"로 좁혀 추가한다.
