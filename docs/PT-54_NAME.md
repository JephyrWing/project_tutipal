## 동작과 API

- 최초 가입에만 소셜 제공자의 이름을 초기값으로 사용한다. 기존 계정의 이름은 이후 소셜·개발 로그인에서 덮어쓰지 않는다.
- 설정 → 계정에서 이름을 수정한다. 저장 응답으로 현재 화면의 인증 사용자 정보를 갱신한다.
- `PATCH /api/users/me/name`, JSON `{ "name": "새 이름" }`.
- 응답은 기존 `UserResponse`: `id`, `name`, `provider`, `role`. 이메일·제공자 사용자 ID는 노출하지 않는다.
- 변경 대상은 세션 principal의 본인 ID로만 정한다. 기존 로그인 세션과 CSRF 검사를 유지한다.
- 앞뒤 Unicode 공백을 제거하고 비어 있는 이름, 50 UTF-16 코드 단위를 초과한 이름, 내부 제어문자를 400으로 거절한다.
  프론트 입력도 `maxLength=50`을 사용한다. 이름 중복은 허용한다.
- 기존 `users.name`을 사용하며 migration이나 기존 데이터 일괄 변경은 없다.
- 이름은 표시용이며 계정 식별은 기존 provider/providerId와 내부 ID를 유지한다.
- 소셜 제공자에서 바꾼 이름도 기존 계정에 자동 반영하지 않는다. 앱 이름 변경은 설정 화면에서 수행한다.
- 기존 사용자 이름을 조회하는 화면은 이후 조회 시 변경한 값을 사용한다. 과거 문서/스냅샷을 일괄 수정하거나
  다른 실행 중인 앱 창에 변경을 즉시 방송하는 기능은 이번 단위에 포함하지 않는다.

## 검증과 한계

- `UserServiceNameTest`: 최초 가입, 기존 계정 이름 보존, 수정 후 반복 소셜 로그인 경로, 길이·공백·제어문자·계정 없음.
- `UserNameWebTest`: 실제 controller/service/SecurityConfig와 모의 저장소로 인증·CSRF·본인 ID·역할 보존·오류를 확인한다.
- `tests/e2e/profile-name.spec.js`: 실제 Spring/임시 PostgreSQL/Electron에서 이름 저장·새로고침·개발 재로그인·타인 계정 보존,
  저장 실패 후 재시도를 확인한다. 개발 로그인은 소셜 로그인과 같은 `UserService.upsert`를 사용한다.
- 실계정 OAuth 리디렉션·실서비스 인증은 위 검사로 대체하지 않는다. 실제 실행 결과·최종 SHA·CI 링크는 PT-54에 기록한다.
- 학습 기록 조회, 소셜 계정 연결·해제, 탈퇴 및 PT-54 전체 기능 인수는 이번 이름 수정 단위와 별도다.
- 변경은 develop 대상 PR로 제출하며 PM 직접 확인·완료와 실제 병합은 별도 상태로 관리한다.
