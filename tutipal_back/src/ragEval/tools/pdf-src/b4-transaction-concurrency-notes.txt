데이터베이스 강의 노트 - 트랜잭션과 동시성 제어
(팀 작성 자료, 9주차 수업용)

제1장 트랜잭션의 개념

1.1 트랜잭션이 필요한 이유

트랜잭션은 데이터베이스에서 하나의 논리적 작업 단위를 이루는 연산들의 묶음이다. 계좌 A에서 B로 10만 원을 이체하는 작업은 "A의 잔액에서 10만 원 빼기"와 "B의 잔액에 10만 원 더하기"라는 두 개의 UPDATE로 이루어지는데, 첫 번째 문장만 실행된 뒤 서버 전원이 꺼지면 10만 원이 허공으로 사라진다. 트랜잭션으로 두 문장을 묶으면 둘 다 반영되거나 둘 다 반영되지 않는 것 중 하나만 일어난다. SQL에서는 BEGIN으로 시작해 COMMIT으로 확정하고, 중간에 문제가 생기면 ROLLBACK으로 시작 전 상태로 되돌린다.

1.2 ACID 성질

트랜잭션이 보장해야 하는 네 가지 성질을 머리글자를 따서 ACID라고 부른다. 원자성(Atomicity)은 트랜잭션의 연산이 전부 실행되거나 전혀 실행되지 않아야 한다는 성질이며, DBMS는 언두 로그를 남겨 두었다가 실패 시 변경을 거꾸로 되돌리는 방식으로 이를 구현한다. 일관성(Consistency)은 트랜잭션 전후로 "잔액은 음수가 될 수 없다" 같은 무결성 제약이 항상 지켜져야 한다는 성질이다. 고립성(Isolation)은 동시에 실행되는 트랜잭션들이 서로의 중간 결과를 보지 못하고, 마치 하나씩 차례로 실행된 것처럼 보여야 한다는 성질이다. 지속성(Durability)은 COMMIT이 성공했다고 응답한 변경은 그 직후 장애가 나더라도 사라지지 않아야 한다는 성질로, 변경 내용을 데이터 파일보다 먼저 로그에 기록하는 선행 기록 로그(WAL) 기법으로 구현한다.

네 성질 가운데 이번 주의 주제는 고립성이다. 고립성을 완벽하게 지키는 가장 쉬운 방법은 트랜잭션을 한 번에 하나씩만 실행하는 것이지만, 그러면 디스크 입출력을 기다리는 동안 CPU가 놀게 되고 초당 처리할 수 있는 트랜잭션 수가 크게 떨어진다. 동시성 제어는 여러 트랜잭션을 겹쳐 실행하면서도 결과가 어떤 직렬 실행 순서와 같도록 만드는 기술이다.

제2장 동시 실행에서 생기는 문제

2.1 갱신 손실과 오손 읽기

재고가 10개인 상품을 두 주문 트랜잭션 T1과 T2가 동시에 처리한다고 하자. T1이 재고 10을 읽고, T2도 10을 읽은 뒤, T1이 9를 쓰고 T2도 9를 쓰면 두 개가 팔렸는데 재고는 9로 남는다. 이를 갱신 손실이라고 한다. 오손 읽기(dirty read)는 아직 COMMIT되지 않은 다른 트랜잭션의 변경을 읽는 현상이다. T1이 잔액을 50만 원에서 0원으로 바꾼 상태에서 T2가 0원을 읽고 대출을 거절했는데, 이후 T1이 ROLLBACK되면 T2는 존재한 적 없는 값을 근거로 판단한 셈이 된다.

2.2 반복 불가능한 읽기와 팬텀

반복 불가능한 읽기(non-repeatable read)는 한 트랜잭션 안에서 같은 행을 두 번 읽었는데 그사이 다른 트랜잭션이 그 행을 수정하고 COMMIT해서 값이 달라지는 현상이다. 팬텀 읽기는 같은 조건으로 두 번 조회했을 때 다른 트랜잭션이 새로 삽입한 행이 두 번째 결과에 유령처럼 나타나는 현상이다. 예를 들어 "급여가 300만 원 이상인 직원 수"를 집계하는 보고서 트랜잭션이 첫 조회에서 42명을 얻었는데, 그사이 신규 직원 한 명이 추가되면 두 번째 조회에서는 43명이 나온다. 반복 불가능한 읽기는 기존 행의 값이 바뀌는 문제이고, 팬텀은 조건을 만족하는 행의 집합 자체가 바뀌는 문제라는 점이 다르다.

2.3 SQL 표준의 격리 수준

SQL 표준은 위 현상을 어디까지 허용하느냐에 따라 네 가지 격리 수준을 정의한다. READ UNCOMMITTED는 오손 읽기까지 허용한다. READ COMMITTED는 COMMIT된 데이터만 읽게 해서 오손 읽기를 막지만, 반복 불가능한 읽기와 팬텀은 생길 수 있다. REPEATABLE READ는 한 번 읽은 행은 트랜잭션이 끝날 때까지 같은 값으로 보이도록 보장하며, 표준상으로는 팬텀만 허용한다. SERIALIZABLE은 모든 현상을 막아 직렬 실행과 같은 결과를 보장한다.

제품마다 기본값과 실제 동작이 다르다는 점에 주의해야 한다. PostgreSQL과 Oracle의 기본 격리 수준은 READ COMMITTED이고, MySQL의 InnoDB 엔진은 REPEATABLE READ가 기본이다. 또 InnoDB의 REPEATABLE READ는 일반 SELECT에서 스냅샷을 사용하기 때문에 표준과 달리 대부분의 팬텀도 보이지 않는다. PostgreSQL은 READ UNCOMMITTED를 지정해도 실제로는 READ COMMITTED로 동작한다. 수강생 프로젝트에서 "로컬에서는 되는데 서버에서는 이상하다"는 질문의 상당수가 개발용 DB와 운영 DB의 격리 수준 차이에서 나왔으므로, 설정 파일에 격리 수준을 명시하는 습관을 들이자.

제3장 잠금 기반 동시성 제어

3.1 공유 잠금과 배타 잠금

가장 널리 쓰이는 동시성 제어 방법은 데이터 항목에 잠금을 거는 것이다. 읽기를 위한 공유 잠금(S 잠금)은 여러 트랜잭션이 동시에 가질 수 있지만, 쓰기를 위한 배타 잠금(X 잠금)은 한 트랜잭션만 가질 수 있고 S 잠금과도 함께 존재할 수 없다. 즉 S와 S는 호환되고, S와 X, X와 X는 호환되지 않는다. 잠금의 단위가 행이면 동시성은 높지만 관리할 잠금 수가 많아지고, 테이블 단위면 관리 비용은 작지만 동시에 실행할 수 있는 트랜잭션이 줄어든다.
<<<PAGE>>>
SQL에서는 SELECT ... FOR UPDATE로 읽는 순간 해당 행에 배타 잠금을 걸 수 있다. 앞의 재고 예시에서 두 주문 트랜잭션이 모두 FOR UPDATE로 재고를 읽으면, T2는 T1이 COMMIT할 때까지 기다린 뒤 갱신된 값 9를 읽으므로 갱신 손실이 생기지 않는다. 대신 대기 시간이 늘어나므로 잠금을 쥔 채로 외부 API를 호출하거나 사용자 입력을 기다리는 코드는 피해야 한다. 실습 환경에서 잠금을 쥔 채 2초짜리 외부 결제 모의 호출을 넣었더니, 동시 요청 50건의 평균 응답 시간이 0.3초에서 30초 가까이로 늘어났다.

3.2 2단계 잠금 규약

잠금을 단순히 쓰기만 해서는 직렬 가능성이 보장되지 않는다. 2단계 잠금(2PL) 규약은 트랜잭션을 잠금을 얻기만 하는 확장 단계와 잠금을 풀기만 하는 축소 단계로 나누고, 한 번이라도 잠금을 풀었다면 그 뒤로는 새 잠금을 얻을 수 없게 한다. 모든 트랜잭션이 2PL을 따르면 그 스케줄은 충돌 직렬 가능하다는 것이 증명되어 있다.

기본 2PL에서는 축소 단계에 일찍 푼 잠금 때문에 다른 트랜잭션이 아직 COMMIT되지 않은 값을 읽을 수 있고, 원래 트랜잭션이 ROLLBACK되면 그 값을 읽은 트랜잭션까지 연쇄적으로 되돌려야 하는 연쇄 복귀가 생긴다. 그래서 실제 DBMS는 배타 잠금을 COMMIT이나 ROLLBACK 시점까지 유지하는 엄격한 2PL(strict 2PL)이나, 모든 잠금을 끝까지 유지하는 강한 엄격 2PL을 사용한다.

제4장 데이터베이스에서의 교착 상태

4.1 대기 그래프로 탐지하기

잠금을 쓰면 교착 상태를 피할 수 없다. T1이 계좌 A의 행에 X 잠금을 걸고 B를 기다리는 동안, T2가 B에 X 잠금을 걸고 A를 기다리면 두 트랜잭션은 서로를 영원히 기다린다. 데이터베이스는 이를 트랜잭션을 정점으로, "Ti가 Tj가 가진 잠금을 기다린다"를 Ti에서 Tj로 가는 간선으로 하는 대기 그래프(wait-for graph)로 표현하고, 그래프에 사이클이 생기면 교착 상태로 판단한다. 운영체제의 자원 할당 그래프와 달리 대기 그래프에는 자원 정점이 없고 트랜잭션끼리만 연결된다는 점이 다르다.
<<<PAGE>>>
탐지 주기와 방식은 제품마다 다르다. MySQL InnoDB는 잠금 대기가 생길 때마다 즉시 대기 그래프를 검사해 사이클을 찾으며, 탐지 기능을 끈 경우에는 innodb_lock_wait_timeout(기본값 50초)이 지나면 대기 중인 문장을 실패시킨다. PostgreSQL은 잠금을 기다리기 시작한 뒤 deadlock_timeout(기본값 1초)만큼 지나도 잠금을 얻지 못했을 때만 교착 상태 검사를 수행한다. 검사 자체의 비용이 작지 않기 때문에, 대부분의 잠금 대기는 1초 안에 자연스럽게 풀린다는 가정 아래 검사를 미루는 것이다.

4.2 희생자 선택과 응용 프로그램의 대응

사이클을 찾으면 DBMS는 사이클에 속한 트랜잭션 하나를 희생자로 골라 ROLLBACK시키고 잠금을 풀어 나머지를 진행시킨다. InnoDB는 변경한 행 수가 적은, 즉 되돌리는 비용이 작은 트랜잭션을 희생자로 고르는 경향이 있다. 희생된 트랜잭션의 클라이언트는 MySQL에서 오류 코드 1213, PostgreSQL에서 SQLSTATE 40P01을 받는다. 이 오류는 버그가 아니라 정상적인 동시성 제어의 결과이므로, 응용 프로그램은 트랜잭션 전체를 처음부터 다시 시도하도록 작성해야 한다. 재시도는 무한히 하지 말고 3회 정도로 제한하며, 매번 수십 밀리초씩 간격을 늘려 같은 충돌이 반복되지 않게 한다.

예방 측면에서는 모든 트랜잭션이 같은 순서로 행을 잠그도록 하는 것이 가장 효과적이다. 계좌 이체라면 계좌 번호가 작은 쪽부터 잠그는 규칙 하나로 앞의 T1, T2 같은 교착 상태가 사라진다. 이론적으로는 트랜잭션 시작 시각을 기준으로 오래된 트랜잭션이 젊은 트랜잭션을 기다리기만 하는 wait-die 방식이나, 오래된 트랜잭션이 젊은 트랜잭션을 강제로 철회시키는 wound-wait 방식도 있지만, 범용 관계형 DBMS는 주로 탐지 후 희생자 선택 방식을 쓴다.

제5장 다중 버전 동시성 제어

5.1 MVCC의 아이디어

잠금 방식에서는 읽기와 쓰기가 서로를 막는다. 다중 버전 동시성 제어(MVCC)는 행을 수정할 때 덮어쓰지 않고 새 버전을 만들어, 읽는 트랜잭션은 자신이 시작한 시점에 COMMIT되어 있던 버전을 보게 한다. 그 결과 "읽기는 쓰기를 막지 않고, 쓰기는 읽기를 막지 않는다." 쓰기끼리는 여전히 행 잠금으로 충돌을 처리한다.
<<<PAGE>>>
구현 방식은 제품마다 다르다. PostgreSQL은 테이블 안에 이전 버전의 행을 그대로 남겨 두고, 각 행에 그 버전을 만든 트랜잭션 번호(xmin)와 지운 트랜잭션 번호(xmax)를 기록해 어떤 트랜잭션에게 보일지를 판단한다. 더 이상 아무도 볼 필요가 없는 옛 버전은 VACUUM이 정리하며, 오래 열려 있는 트랜잭션이 하나라도 있으면 그보다 새로운 옛 버전을 지울 수 없어 테이블이 계속 부풀어 오른다. MySQL InnoDB와 Oracle은 최신 버전만 테이블에 두고 이전 값은 언두 영역에 저장했다가, 과거 스냅샷이 필요한 트랜잭션에게 언두 기록을 거꾸로 적용해 옛 버전을 재구성해 준다.

스냅샷을 언제 찍느냐가 곧 격리 수준의 차이가 된다. PostgreSQL의 READ COMMITTED에서는 SQL 문장 하나가 시작될 때마다 새 스냅샷을 찍기 때문에, 같은 트랜잭션 안에서도 두 번째 SELECT는 그사이 COMMIT된 변경을 본다. REPEATABLE READ에서는 트랜잭션의 첫 문장이 실행될 때 찍은 스냅샷 하나를 끝까지 사용하므로, 다른 트랜잭션이 아무리 많은 행을 고쳐도 처음 본 데이터가 그대로 보인다. 다만 이 수준에서 다른 트랜잭션이 이미 고치고 COMMIT한 행을 다시 수정하려 하면, PostgreSQL은 옛 값을 덮어쓰는 대신 SQLSTATE 40001 직렬화 실패 오류를 돌려준다. 수업 실습에서 두 터미널로 같은 행을 번갈아 수정해 보면, READ COMMITTED에서는 뒤에 온 UPDATE가 앞 트랜잭션의 COMMIT을 기다렸다가 새 값 위에 그대로 적용되고, REPEATABLE READ에서는 같은 순서로 실행해도 뒤에 온 쪽이 오류로 끝나는 차이를 직접 확인할 수 있다.

MVCC의 비용도 함께 기억해야 한다. 옛 버전을 보관하는 공간이 필요하고, 버전이 쌓일수록 원하는 버전을 찾기 위해 읽어야 하는 데이터가 늘어난다. 실습용 테이블에서 한 트랜잭션을 30분 동안 열어 둔 채 다른 세션에서 같은 테이블의 행 100만 개를 다섯 번 갱신했더니, 테이블 크기가 약 70MB에서 400MB 가까이로 불어났고 열린 트랜잭션을 닫고 VACUUM을 실행한 뒤에야 공간이 재사용되기 시작했다. 운영 환경에서 "idle in transaction" 상태의 세션을 감시하는 이유가 여기에 있다.

5.2 스냅샷 격리와 쓰기 왜곡

MVCC 위에서 트랜잭션 시작 시점의 스냅샷만 읽게 하는 것을 스냅샷 격리라고 한다. 스냅샷 격리는 오손 읽기, 반복 불가능한 읽기, 팬텀을 모두 막지만 직렬 가능성을 보장하지는 않는다. 대표적인 반례가 쓰기 왜곡(write skew)이다. 병원에서 "당직 의사는 최소 1명 있어야 한다"는 규칙이 있고 현재 당직이 두 명이라고 하자. 두 의사가 동시에 당직 해제를 요청하면, 각 트랜잭션은 자신의 스냅샷에서 당직이 두 명인 것을 확인하고 자기 행만 수정한다. 두 트랜잭션이 고친 행이 서로 달라 쓰기 충돌이 감지되지 않으므로 둘 다 COMMIT되고, 결국 당직 의사가 0명이 된다.

PostgreSQL은 9.1 버전부터 SERIALIZABLE 수준에서 직렬화 가능 스냅샷 격리(SSI)를 사용해, 트랜잭션 사이의 읽기-쓰기 의존 관계를 추적하다가 위험한 구조가 생기면 한쪽을 SQLSTATE 40001 오류로 실패시킨다. 이 경우에도 응용 프로그램은 교착 상태와 마찬가지로 트랜잭션을 재시도해야 한다.

5.3 정리

정리하면, 동시성 제어는 성능과 정확성 사이의 균형을 고르는 일이다. 격리 수준을 높일수록 이상 현상은 줄지만 대기와 재시도가 늘어난다. 실무에서는 대부분의 조회를 READ COMMITTED에서 처리하고, 재고 차감이나 좌석 예약처럼 정확성이 중요한 구간만 SELECT ... FOR UPDATE나 SERIALIZABLE로 보호하는 방식을 많이 쓴다. 다음 주에는 장애가 났을 때 WAL과 체크포인트로 데이터베이스를 복구하는 과정을 다룬다.
