운영체제 강의 노트 - 프로세스, 스레드, 동기화
(팀 작성 자료, 5주차 수업용)

제1장 프로세스와 스레드

1.1 프로세스란 무엇인가

프로그램은 디스크에 저장된 실행 파일이고, 프로세스는 그 프로그램이 메모리에 올라가 실행 중인 상태를 말한다. 같은 메모장 프로그램을 두 번 실행하면 실행 파일은 하나지만 프로세스는 두 개가 생긴다. 운영체제는 각 프로세스에 독립된 가상 주소 공간을 주는데, 이 공간은 보통 코드 영역, 전역 변수가 들어가는 데이터 영역, 동적 할당에 쓰이는 힙, 함수 호출 정보가 쌓이는 스택으로 나뉜다. 한 프로세스가 잘못된 포인터로 메모리를 덮어써도 다른 프로세스의 메모리는 망가지지 않는 것이 이 분리 덕분이다.

운영체제는 프로세스마다 프로세스 제어 블록(PCB)이라는 자료구조를 커널 안에 유지한다. PCB에는 프로세스 식별자(PID), 현재 상태, 프로그램 카운터와 레지스터 값, 스케줄링 우선순위, 열린 파일 목록, 메모리 관리 정보가 들어 있다. CPU가 다른 프로세스로 넘어갈 때 현재 레지스터 값을 PCB에 저장하고 다음 프로세스의 PCB에서 값을 복원하는데, 이것을 문맥 교환이라고 부른다.

1.2 프로세스의 상태 변화

프로세스는 생성(new), 준비(ready), 실행(running), 대기(waiting), 종료(terminated)의 다섯 상태를 오간다. 준비 상태는 CPU만 주어지면 바로 실행할 수 있는 상태이고, 대기 상태는 디스크 읽기나 키보드 입력처럼 어떤 사건이 끝나기를 기다리는 상태다. 실행 중인 프로세스가 할당된 시간 조각을 다 쓰면 타이머 인터럽트가 발생해 준비 상태로 돌아가고, 입출력을 요청하면 대기 상태로 간다. 입출력이 끝나면 대기 상태에서 곧바로 실행으로 가는 것이 아니라 먼저 준비 상태로 옮겨진다는 점이 시험에 자주 나온다.

1.3 스레드와 멀티스레딩

스레드는 프로세스 안에서 실행 흐름의 단위다. 같은 프로세스에 속한 스레드들은 코드, 데이터, 힙, 열린 파일을 공유하고, 각자 자신만의 스택과 레지스터, 프로그램 카운터를 가진다. 웹 서버가 요청마다 프로세스를 새로 만드는 대신 스레드를 만들면, 주소 공간을 복사할 필요가 없어 생성 비용이 작고 문맥 교환 때 페이지 테이블을 바꾸지 않아도 되므로 전환도 빠르다.

리눅스에서 측정해 보면 fork로 프로세스를 만드는 데 수십 마이크로초가 걸리는 반면, 스레드 생성은 그보다 몇 배 짧은 시간에 끝나는 경우가 많다. 다만 메모리를 공유한다는 장점은 그대로 위험이 되기도 한다. 한 스레드가 잘못된 주소에 접근해 세그멘테이션 오류가 나면 같은 프로세스의 모든 스레드가 함께 종료되고, 여러 스레드가 같은 변수를 동시에 고치면 뒤에서 다룰 경쟁 상태가 생긴다. 크롬 브라우저가 탭마다 별도의 프로세스를 쓰는 이유도 한 탭의 오류가 브라우저 전체를 죽이지 않도록 격리하기 위해서다.

사용자 수준 스레드와 커널 수준 스레드의 구분도 알아 두자. 커널이 직접 관리하는 커널 스레드는 하나가 입출력으로 대기해도 다른 스레드가 다른 CPU 코어에서 계속 실행될 수 있다. 사용자 수준 라이브러리만으로 만든 스레드는 전환이 매우 빠르지만, 커널은 이를 하나의 실행 단위로만 보기 때문에 한 스레드의 블로킹 시스템 호출이 프로세스 전체를 멈추게 할 수 있다. Java 21의 가상 스레드는 많은 수의 가벼운 스레드를 소수의 플랫폼 스레드 위에 올려 실행하는 방식으로 이 두 장점을 섞으려는 시도다.

제2장 CPU 스케줄링

2.1 스케줄링의 목표와 지표

준비 상태의 프로세스가 여러 개일 때 누구에게 CPU를 줄지 정하는 것이 CPU 스케줄링이다. 평가 지표로는 CPU 이용률, 단위 시간당 완료한 작업 수인 처리량, 도착부터 완료까지 걸린 반환 시간, 준비 큐에서 기다린 시간의 합인 대기 시간, 요청 후 첫 반응까지 걸린 응답 시간을 쓴다. 대화형 시스템에서는 응답 시간이, 배치 시스템에서는 처리량이 더 중요하다.

2.2 대표적인 스케줄링 알고리즘

선입선출(FCFS)은 도착한 순서대로 실행한다. 구현이 쉽지만, 실행 시간이 24ms인 P1 뒤에 3ms짜리 P2와 P3이 도착하면 평균 대기 시간이 (0 + 24 + 27) / 3 = 17ms가 된다. 같은 작업을 P2, P3, P1 순서로 실행하면 평균 대기 시간은 (0 + 3 + 6) / 3 = 3ms로 줄어든다. 긴 작업 하나 때문에 짧은 작업들이 줄줄이 기다리는 이 현상을 호위 효과라고 한다.

최단 작업 우선(SJF)은 실행 시간이 가장 짧은 작업부터 실행해 평균 대기 시간을 최소로 만든다는 것이 증명되어 있다. 그러나 다음 CPU 사용 시간을 미리 알 수 없으므로 과거 사용 시간의 지수 평균으로 예측한다. 또한 짧은 작업이 계속 들어오면 긴 작업이 영원히 실행되지 못하는 기아 현상이 생길 수 있어, 기다린 시간만큼 우선순위를 올려 주는 에이징 기법을 함께 쓴다.
<<<PAGE>>>
라운드 로빈(RR)은 각 프로세스에 정해진 시간 할당량만큼만 CPU를 주고, 다 쓰면 준비 큐의 맨 뒤로 보낸다. 시간 할당량이 너무 크면 FCFS와 다를 바 없어지고, 너무 작으면 문맥 교환 비용이 실제 작업 시간을 잡아먹는다. 문맥 교환에 0.1ms가 걸린다고 할 때 할당량을 1ms로 잡으면 CPU 시간의 약 9%가 전환에 쓰이지만, 10ms로 잡으면 약 1%로 줄어든다. 교재에서는 CPU 사용 구간의 80% 정도가 할당량 안에 끝나도록 정하는 것을 경험칙으로 소개한다.

리눅스는 2007년 커널 2.6.23부터 완전 공정 스케줄러(CFS)를 사용해 왔다. CFS는 각 태스크가 실제로 CPU를 쓴 시간을 가중치로 나눈 가상 실행 시간을 기록하고, 이 값이 가장 작은 태스크를 레드-블랙 트리의 가장 왼쪽 노드에서 꺼내 실행한다. 이후 커널 6.6부터는 EEVDF라는 새로운 스케줄러로 교체되었지만, 가상 실행 시간으로 공정성을 맞춘다는 기본 아이디어는 이어지고 있다.

제3장 프로세스 동기화

3.1 경쟁 상태와 임계 구역

두 스레드가 공유 변수 count를 각각 1씩 증가시키는 상황을 생각해 보자. count++는 한 줄짜리 코드지만 기계어 수준에서는 메모리에서 레지스터로 읽기, 레지스터 값 1 증가, 메모리에 다시 쓰기의 세 단계로 나뉜다. 스레드 A가 값 5를 읽은 직후 스레드 B로 전환되어 B도 5를 읽고 6을 쓴 뒤, A가 다시 실행되어 6을 쓰면 두 번 증가시켰는데도 결과는 6이 된다. 이처럼 실행 순서에 따라 결과가 달라지는 상황을 경쟁 상태라고 한다. 실습에서 스레드 두 개가 각각 100만 번씩 증가시키는 프로그램을 돌렸을 때 기대값 200만 대신 120만에서 150만 사이의 값이 매번 다르게 나온 것이 바로 이 때문이다.

공유 자원에 접근하는 코드 구간을 임계 구역이라고 하며, 올바른 해결책은 세 가지 조건을 만족해야 한다. 첫째, 상호 배제: 한 스레드가 임계 구역에 있으면 다른 스레드는 들어갈 수 없다. 둘째, 진행: 임계 구역이 비어 있으면 들어가려는 스레드 중 하나는 유한 시간 안에 들어갈 수 있어야 한다. 셋째, 한정된 대기: 어떤 스레드도 무한정 기다려서는 안 된다.

3.2 하드웨어 지원과 뮤텍스

소프트웨어만으로 상호 배제를 구현한 피터슨 알고리즘은 두 스레드에 대해 세 조건을 모두 만족하지만, 현대 CPU는 명령어 실행 순서를 바꾸기 때문에 메모리 배리어 없이는 제대로 동작하지 않는다. 그래서 실제 시스템은 test-and-set이나 compare-and-swap(CAS) 같은 원자적 하드웨어 명령을 사용한다. CAS는 "메모리 값이 기대값과 같을 때만 새 값으로 바꾸고, 성공 여부를 돌려준다"는 동작을 중간에 끊기지 않고 한 번에 수행한다. Java의 AtomicInteger.incrementAndGet도 내부적으로 이 CAS를 반복 시도하는 방식으로 구현된다.

뮤텍스는 lock과 unlock 두 연산을 제공하는 잠금 도구다. 잠금을 얻지 못한 스레드가 반복문을 돌며 계속 확인하는 방식을 스핀락이라 하고, 잠자는 상태로 바꾸어 CPU를 양보하는 방식을 블로킹 락이라 한다. 스핀락은 문맥 교환이 없어 임계 구역이 몇 마이크로초 이내로 아주 짧을 때 유리하지만, 단일 코어에서는 잠금을 가진 스레드가 실행될 기회를 빼앗으므로 쓸모가 없다.

3.3 세마포어와 모니터

세마포어는 정수 값 S와 두 연산 wait(P)와 signal(V)로 이루어진다. wait는 S를 1 줄이고 그 결과가 음수이면 호출한 스레드를 대기 큐에 넣으며, signal은 S를 1 늘리고 대기 중인 스레드가 있으면 하나를 깨운다. 값이 0과 1만 오가는 이진 세마포어는 뮤텍스처럼 쓰이고, 초기값이 N인 계수 세마포어는 데이터베이스 연결 10개짜리 풀처럼 같은 종류의 자원 N개를 나누어 쓸 때 쓴다. 다만 뮤텍스에는 잠근 스레드만 풀 수 있다는 소유권 개념이 있는 반면, 세마포어는 아무 스레드나 signal을 호출할 수 있다는 차이가 있다.

모니터는 공유 데이터와 그 데이터를 다루는 프로시저를 하나로 묶고, 한 번에 한 스레드만 모니터 안에서 실행되도록 보장하는 고수준 동기화 구조다. 조건이 맞지 않으면 조건 변수에서 wait하고, 다른 스레드가 조건을 바꾼 뒤 signal로 깨운다. Java의 synchronized 블록과 Object의 wait, notify가 모니터의 대표적인 구현이다. 깨어난 스레드는 조건이 여전히 참인지 다시 확인해야 하므로 wait 호출은 if가 아니라 while 반복문 안에 두는 것이 원칙이다.

3.4 고전적인 동기화 문제

생산자-소비자 문제는 크기가 정해진 버퍼에 생산자는 데이터를 넣고 소비자는 꺼내는 상황이다. 버퍼 크기가 N일 때 빈 칸 수를 나타내는 세마포어 empty를 N으로, 채워진 칸 수를 나타내는 full을 0으로, 버퍼 접근을 보호하는 mutex를 1로 초기화한다. 생산자가 wait(mutex)를 wait(empty)보다 먼저 호출하면, 버퍼가 가득 찬 상태에서 잠금을 쥔 채로 잠들어 소비자도 영원히 들어오지 못한다. 세마포어의 호출 순서 하나가 시스템 전체를 멈추게 할 수 있다는 좋은 예다.

식사하는 철학자 문제는 원탁에 앉은 다섯 철학자가 양옆의 젓가락 두 개를 모두 들어야 식사할 수 있는 상황이다. 모든 철학자가 동시에 왼쪽 젓가락을 들면 아무도 오른쪽 젓가락을 얻지 못해 모두가 영원히 기다린다. 해결책으로는 동시에 앉을 수 있는 인원을 네 명으로 제한하기, 두 젓가락을 모두 집을 수 있을 때만 집기, 홀수 번호 철학자는 왼쪽부터 짝수 번호는 오른쪽부터 집게 하기 등이 있다.

제4장 운영체제에서의 교착 상태

4.1 발생 조건과 자원 할당 그래프

앞의 철학자 문제처럼 프로세스들이 서로가 가진 자원을 기다리며 아무도 진행하지 못하는 상태를 교착 상태라고 한다. 교착 상태는 상호 배제, 점유 대기, 비선점, 순환 대기의 네 조건이 동시에 성립할 때만 발생한다. 운영체제 수업에서는 이를 자원 할당 그래프로 그려서 판단한다. 프로세스는 원, 자원 유형은 사각형으로 그리고, 요청은 프로세스에서 자원으로, 할당은 자원에서 프로세스로 화살표를 긋는다. 모든 자원 유형의 인스턴스가 하나씩이라면 그래프에 사이클이 있다는 것이 곧 교착 상태라는 뜻이지만, 인스턴스가 여러 개인 자원이 있으면 사이클이 있어도 교착 상태가 아닐 수 있다.

4.2 예방, 회피, 탐지와 회복

예방은 네 조건 중 하나를 원천적으로 막는 방법이다. 가장 실용적인 것은 순환 대기를 없애는 자원 순서 규칙으로, 모든 잠금에 번호를 매기고 항상 작은 번호부터 얻게 하면 사이클이 생길 수 없다. 리눅스 커널 개발에서 쓰는 lockdep 도구는 실행 중 잠금 획득 순서를 기록해 이 규칙을 어기는 코드를 찾아낸다.

회피는 자원을 내주기 전에 그 결과가 안전 상태인지 검사하는 방법이며, 대표적인 것이 다익스트라의 은행원 알고리즘이다. 각 프로세스가 앞으로 필요로 할 최대 자원 수를 미리 신고받고, 요청을 들어주었을 때도 모든 프로세스를 어떤 순서로든 끝까지 실행시킬 수 있는 안전 순서가 존재할 때만 할당한다. 예를 들어 자원이 12개인 시스템에서 P0, P1, P2의 최대 요구가 10, 4, 9개이고 현재 5, 2, 2개를 가지고 있다면 남은 자원은 3개다. 이때 P1에 2개를 더 주어 끝내고 반납받으면 5개가 되고, 그다음 P0, P2 순서로 진행할 수 있으므로 안전 상태다. 개념은 깔끔하지만 최대 요구량을 미리 알기 어렵고 검사 비용이 프로세스 수와 자원 종류 수의 곱에 비례해 커서 범용 운영체제에서는 거의 쓰지 않는다.

탐지와 회복은 교착 상태를 일단 허용하고 주기적으로 그래프를 검사해 사이클을 찾은 뒤, 관련 프로세스를 강제 종료하거나 자원을 선점해 푸는 방식이다. 어떤 프로세스를 희생시킬지는 우선순위, 지금까지 실행한 시간, 사용 중인 자원 수 등을 보고 정한다. 실제 윈도우나 리눅스 같은 범용 운영체제는 사용자 프로그램 사이의 교착 상태를 대부분 무시하는 쪽을 택한다. 발생 빈도가 낮은데 예방하거나 탐지하는 비용은 항상 들기 때문이며, 이를 흔히 타조 알고리즘이라고 부른다. 결국 교착 상태를 피하는 책임은 잠금 순서를 정하고 타임아웃을 거는 응용 프로그램 개발자에게 넘어간다.

4.3 정리와 다음 주 예고

이번 주에는 프로세스와 스레드의 차이, CPU 스케줄링의 기본 알고리즘, 경쟁 상태를 막는 동기화 도구, 그리고 동기화를 잘못 썼을 때 생기는 교착 상태를 다루었다. 핵심은 "공유하면 빠르지만 위험하다"는 한 문장으로 요약할 수 있다. 다음 주에는 가상 메모리와 페이지 교체를 다루며, 프로세스마다 독립된 주소 공간을 준다는 이번 주의 설명이 실제로 페이지 테이블과 TLB를 통해 어떻게 구현되는지 살펴본다. 과제로는 생산자-소비자 문제를 세마포어 버전과 Java의 BlockingQueue 버전으로 각각 구현하고, 생산자와 소비자 스레드 수를 1, 2, 4, 8개로 바꾸어 가며 초당 처리량을 비교해 제출한다.
