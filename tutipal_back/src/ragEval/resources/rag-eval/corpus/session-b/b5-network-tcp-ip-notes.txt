컴퓨터 네트워크 강의 노트 - TCP/IP와 전송 계층
(팀 작성 자료, 11주차 수업용)

제1장 계층 구조로 네트워크 바라보기

1.1 왜 계층으로 나누는가

네트워크 통신은 전기 신호를 보내는 일부터 웹 페이지를 화면에 그리는 일까지 수많은 작업으로 이루어진다. 이를 한 덩어리로 설계하면 무선랜을 유선랜으로 바꾸기만 해도 프로그램 전체를 고쳐야 한다. 그래서 통신 기능을 여러 계층으로 나누고, 각 계층은 바로 아래 계층이 제공하는 서비스만 이용해 바로 위 계층에 서비스를 제공하도록 한다. 택배에 비유하면 보내는 사람은 송장만 쓰면 되고, 물건이 트럭으로 가는지 비행기로 가는지는 신경 쓰지 않아도 되는 것과 같다.

국제표준화기구(ISO)의 OSI 참조 모델은 물리, 데이터 링크, 네트워크, 전송, 세션, 표현, 응용의 7계층으로 나눈다. 실제 인터넷은 이보다 단순한 TCP/IP 모델을 따르며, 보통 링크 계층, 인터넷 계층, 전송 계층, 응용 계층의 4계층으로 설명한다. OSI의 세션과 표현 계층 기능은 TCP/IP에서는 대부분 응용 프로그램이나 TLS 같은 라이브러리가 맡는다.

1.2 캡슐화와 각 계층의 데이터 단위

응용 프로그램이 보낸 데이터는 아래 계층으로 내려가면서 계층마다 자신의 헤더를 앞에 붙인다. 전송 계층은 포트 번호가 담긴 TCP 또는 UDP 헤더를 붙여 세그먼트(UDP는 데이터그램)를 만들고, 인터넷 계층은 출발지와 목적지 IP 주소가 담긴 IP 헤더를 붙여 패킷을 만들며, 링크 계층은 MAC 주소가 담긴 이더넷 헤더와 오류 검사용 트레일러를 붙여 프레임을 만든다. 받는 쪽에서는 반대로 한 계층씩 올라가면서 헤더를 떼어 낸다. 이더넷 프레임이 실어 나를 수 있는 데이터의 최대 크기인 MTU는 보통 1,500바이트이고, 여기서 IPv4 헤더 20바이트와 TCP 헤더 20바이트를 빼면 한 세그먼트에 담을 수 있는 응용 데이터는 최대 1,460바이트가 된다. 이 값을 MSS라고 한다.

제2장 인터넷 계층과 IP

2.1 IP 주소와 서브넷

IPv4 주소는 32비트로, 8비트씩 끊어 192.168.0.10처럼 점으로 구분한 십진수 네 개로 쓴다. 주소는 네트워크를 나타내는 앞부분과 그 네트워크 안의 호스트를 나타내는 뒷부분으로 나뉘며, 경계는 서브넷 마스크나 /24 같은 CIDR 표기로 나타낸다. 192.168.0.0/24라면 앞 24비트가 네트워크 부분이고 남은 8비트로 256개의 주소를 만들 수 있는데, 모든 비트가 0인 네트워크 주소와 모두 1인 브로드캐스트 주소를 빼면 실제 호스트에 줄 수 있는 주소는 254개다. 32비트로 만들 수 있는 주소는 약 43억 개뿐이라 이미 고갈되었고, 이를 해결하기 위해 128비트 주소를 쓰는 IPv6와, 사설 주소 여러 개를 공인 주소 하나로 바꿔 주는 NAT가 함께 쓰이고 있다.

2.2 IP의 서비스 특성

IP는 패킷을 목적지까지 최선을 다해 전달하려 하지만 아무것도 보장하지 않는다. 패킷이 중간에 사라질 수도 있고, 보낸 순서와 다르게 도착할 수도 있으며, 같은 패킷이 두 번 도착할 수도 있다. 각 패킷은 독립적으로 라우팅되므로 같은 연결의 패킷이라도 서로 다른 경로로 갈 수 있다. IP 헤더의 TTL 필드는 라우터를 하나 지날 때마다 1씩 줄어들어 0이 되면 패킷을 버리게 하는데, 이는 라우팅 오류로 패킷이 영원히 떠도는 것을 막기 위한 장치다. traceroute 명령은 TTL을 1, 2, 3으로 늘려 가며 보내고 각 라우터가 돌려주는 오류 메시지를 이용해 경로를 알아낸다.

제3장 전송 계층: TCP와 UDP

3.1 포트와 소켓

IP 주소가 컴퓨터를 찾아가는 주소라면, 포트 번호는 그 컴퓨터 안에서 어느 프로그램에 데이터를 전달할지 정하는 16비트 번호다. 0번부터 1023번까지는 잘 알려진 포트로, HTTP는 80번, HTTPS는 443번, SSH는 22번, DNS는 53번을 쓴다. 하나의 TCP 연결은 출발지 IP, 출발지 포트, 목적지 IP, 목적지 포트, 프로토콜의 다섯 값으로 구별된다. 그래서 웹 서버가 443번 포트 하나로 수천 개의 연결을 동시에 받을 수 있다. 클라이언트 쪽 포트는 운영체제가 49152번 이상의 임시 포트 가운데 하나를 골라 준다.

3.2 TCP 연결 설정: 3방향 핸드셰이크

TCP는 데이터를 보내기 전에 먼저 연결을 맺는다. 클라이언트가 SYN 플래그와 임의의 초기 순서 번호 x를 담은 세그먼트를 보내면, 서버는 SYN과 ACK 플래그를 함께 설정하고 자신의 초기 순서 번호 y와 확인 번호 x+1을 담아 응답한다. 마지막으로 클라이언트가 확인 번호 y+1을 담은 ACK를 보내면 연결이 성립한다. 세 번 주고받기 때문에 3방향 핸드셰이크라고 부르며, 연결 설정에만 최소 1 RTT(왕복 시간)가 든다. 서울과 미국 서부 사이의 RTT가 약 130ms라면, 데이터를 한 바이트도 보내기 전에 연결 설정만으로 그만큼의 시간이 지나는 셈이다.

초기 순서 번호를 0부터 시작하지 않고 무작위로 정하는 이유는 두 가지다. 하나는 이전 연결에서 늦게 도착한 세그먼트가 새 연결의 데이터로 오인되지 않게 하기 위해서이고, 다른 하나는 공격자가 순서 번호를 추측해 가짜 세그먼트를 끼워 넣기 어렵게 하기 위해서다. 연결을 끊을 때는 양쪽이 각자 FIN을 보내고 ACK를 받는 4방향 종료 과정을 거치며, 먼저 끊은 쪽은 늦게 도착하는 세그먼트를 처리하기 위해 TIME_WAIT 상태에서 최대 세그먼트 수명의 두 배(리눅스에서는 60초) 동안 기다린다.

3.3 신뢰성 있는 전달

TCP는 IP 위에서 손실도, 중복도, 순서 바뀜도 없는 바이트 스트림을 제공한다. 보내는 쪽은 각 바이트에 순서 번호를 매기고, 받는 쪽은 다음에 받기를 기대하는 바이트의 번호를 확인 응답(ACK)으로 돌려준다. 보낸 세그먼트에 대한 ACK가 재전송 타임아웃(RTO) 안에 오지 않으면 그 세그먼트를 다시 보낸다. RTO는 측정한 RTT의 평균과 변동폭으로 계산하며, 재전송이 실패할 때마다 두 배씩 늘린다. 또 같은 ACK가 세 번 중복해서 도착하면 타임아웃을 기다리지 않고 바로 해당 세그먼트를 다시 보내는데, 이를 빠른 재전송이라고 한다.

3.4 흐름 제어와 혼잡 제어

흐름 제어는 받는 쪽의 버퍼가 넘치지 않도록 보내는 속도를 맞추는 기능이다. 받는 쪽은 ACK에 자신이 더 받을 수 있는 바이트 수인 수신 윈도우를 실어 보내고, 보내는 쪽은 ACK를 받지 않은 데이터가 이 값을 넘지 않게 한다. TCP 헤더의 윈도우 필드는 16비트라 최대 65,535바이트까지만 표현할 수 있으므로, 고속 회선에서는 윈도우 스케일 옵션으로 이 값을 최대 2의 14제곱 배까지 늘린다.

혼잡 제어는 받는 쪽이 아니라 네트워크 자체가 감당할 수 있는 양을 넘지 않도록 하는 기능이다. 보내는 쪽은 혼잡 윈도우(cwnd)라는 값을 따로 유지하고, 실제로 한 번에 보낼 수 있는 양은 수신 윈도우와 혼잡 윈도우 중 작은 값이 된다. 연결 초기에는 슬로 스타트로 cwnd를 작게 시작해 ACK를 받을 때마다 늘리므로, RTT마다 대략 두 배씩 커진다. cwnd가 임계값에 도달하면 RTT마다 1 MSS씩만 늘리는 혼잡 회피 단계로 넘어간다. 패킷 손실을 감지하면 혼잡이 생겼다고 보고 cwnd를 줄이는데, 중복 ACK로 감지했을 때는 절반으로 줄이고 타임아웃이 났을 때는 처음부터 다시 슬로 스타트를 한다. 이처럼 천천히 늘리고 손실 시 크게 줄이는 방식을 AIMD라고 부른다. 리눅스의 기본 혼잡 제어 알고리즘은 CUBIC이며, 구글이 개발한 BBR은 손실 대신 측정한 대역폭과 RTT를 바탕으로 보내는 속도를 정한다.

3.5 UDP와의 비교

UDP는 포트 번호와 길이, 체크섬만 담은 8바이트짜리 헤더를 붙여 데이터를 보낼 뿐, 연결 설정도 재전송도 순서 보장도 하지 않는다. 대신 핸드셰이크가 없어 첫 데이터를 곧바로 보낼 수 있고, 헤더가 TCP의 최소 20바이트보다 작으며, 메시지 경계가 유지된다. DNS 조회처럼 요청과 응답이 각각 패킷 하나로 끝나는 경우, 음성 통화나 게임처럼 늦게 온 데이터보다 차라리 버리는 편이 나은 경우에 UDP를 쓴다. 손실 복구가 필요하면 응용 계층에서 직접 구현한다.

HTTP/3의 바탕인 QUIC이 대표적인 예다. QUIC은 UDP 위에서 재전송, 혼잡 제어, 암호화를 직접 구현해, TCP와 TLS를 따로 쓸 때 필요했던 여러 번의 왕복을 줄인다. 처음 접속하는 서버라도 1 RTT, 이전에 접속한 적이 있는 서버라면 0 RTT 만에 암호화된 데이터를 보내기 시작할 수 있다. 또 TCP는 하나의 바이트 스트림이라 앞쪽 세그먼트 하나가 사라지면 뒤에 도착한 데이터도 모두 기다려야 하는 HOL 블로킹이 생기지만, QUIC은 스트림별로 순서를 관리해 한 스트림의 손실이 다른 스트림을 막지 않는다.

제4장 응용 계층과의 연결

4.1 웹 페이지 하나를 여는 동안 일어나는 일

브라우저 주소창에 주소를 입력하면 먼저 DNS로 도메인 이름에 해당하는 IP 주소를 알아낸다. 이어서 그 IP 주소의 443번 포트로 TCP 3방향 핸드셰이크를 하고, TLS 1.3 핸드셰이크로 암호화 키를 합의한 뒤, HTTP 요청을 보내고 응답을 받는다. RTT가 50ms인 환경이라면 DNS 1 RTT, TCP 1 RTT, TLS 1 RTT, HTTP 요청과 응답 1 RTT로, 첫 바이트를 받기까지만 최소 200ms가 걸린다. 그래서 브라우저와 서버는 한 번 맺은 연결을 여러 요청에 재사용하는 keep-alive, DNS 결과 캐시, TLS 세션 재개 같은 방법으로 왕복 횟수를 줄인다.

4.2 실습 안내

이번 주 실습에서는 Wireshark로 수업용 웹 서버에 접속하는 과정을 캡처해, 3방향 핸드셰이크의 순서 번호와 확인 번호가 실제로 x, y, x+1, y+1 관계를 이루는지 확인한다. 이어서 리눅스의 tc 명령으로 패킷 손실률을 0%, 1%, 5%로 바꾸어 가며 100MB 파일을 내려받는 시간을 측정하고, 손실률이 처리량에 미치는 영향을 혼잡 제어의 동작으로 설명하는 보고서를 제출한다.
