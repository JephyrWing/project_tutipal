# 데이터베이스 강의 노트 - 인덱스의 구조와 활용

> 팀 작성 자료 (7주차 수업용). 실습 수치는 수업용 PostgreSQL 16 컨테이너에서 측정한 값이다.

## 1. 인덱스가 필요한 이유

인덱스는 테이블의 특정 열 값으로 행의 위치를 빠르게 찾기 위해 따로 만들어 두는 자료구조다. 책 뒤의 찾아보기를 떠올리면 쉽다. 찾아보기가 없으면 "교착 상태"라는 단어가 나오는 쪽을 찾기 위해 책을 처음부터 끝까지 넘겨야 하지만, 찾아보기가 있으면 가나다순으로 정리된 목록에서 단어를 찾고 적힌 쪽 번호로 바로 이동하면 된다.

데이터베이스에서 인덱스가 없는 조회는 테이블의 모든 페이지를 읽는 전체 테이블 스캔이 된다. 실습에서 주문 테이블에 1,000만 행을 넣고 `WHERE order_no = 'O-20240001'` 조건으로 한 건을 조회했을 때, 인덱스가 없으면 약 1.2초가 걸렸고 B+트리 인덱스를 만든 뒤에는 0.1밀리초 안팎으로 줄었다. 대략 만 배 차이다. 반대로 인덱스는 공짜가 아니다. 행을 삽입하거나 인덱스 열을 수정할 때마다 인덱스도 함께 고쳐야 하므로 쓰기가 느려지고, 인덱스 자체가 디스크 공간을 차지한다. 같은 주문 테이블에 인덱스를 다섯 개 붙였더니 대량 삽입 속도가 인덱스가 없을 때의 약 40% 수준으로 떨어졌다.

## 2. B+트리 인덱스

### 2.1 구조

관계형 데이터베이스의 기본 인덱스는 거의 모두 B+트리다. B+트리는 한 노드에 수백 개의 키를 담는 균형 트리로, 실제 행을 가리키는 정보는 맨 아래 리프 노드에만 있고 내부 노드는 어느 자식으로 내려갈지 알려 주는 길잡이 키만 가진다. 모든 리프 노드는 같은 깊이에 있고, 이웃한 리프끼리 연결 리스트처럼 이어져 있다.

노드 하나는 디스크 페이지 하나에 대응한다. PostgreSQL의 페이지 크기는 8KB, MySQL InnoDB는 16KB다. 키가 8바이트 정수이고 자식 포인터를 포함해 항목 하나가 약 16바이트라면, 8KB 페이지 하나에 약 500개의 항목이 들어간다. 그러면 높이 3인 트리로 500 × 500 × 500, 즉 약 1억 2,500만 개의 키를 다룰 수 있다. 1억 행 테이블에서 한 건을 찾는 데 페이지를 서너 번만 읽으면 된다는 뜻이며, 루트와 그 아래 내부 노드는 대개 메모리 버퍼에 상주하므로 실제 디스크 읽기는 한두 번에 그친다.

### 2.2 이진 탐색 트리와 다른 점

자료구조 시간에 배운 이진 탐색 트리도 O(log n)에 탐색하지만, 노드마다 자식이 둘뿐이라 1억 개의 키를 담으려면 높이가 최소 27이 된다. 메모리 안에서는 문제가 없지만, 노드 하나를 읽을 때마다 디스크 입출력이 한 번씩 일어난다면 27번의 임의 읽기는 너무 비싸다. B+트리는 한 번의 입출력으로 가져오는 페이지에 최대한 많은 키를 담아 트리 높이, 곧 입출력 횟수를 줄이는 쪽으로 설계된 자료구조다.

### 2.3 범위 검색과 정렬

리프 노드가 키 순서대로 연결되어 있기 때문에 B+트리는 범위 조건에 강하다. `WHERE created_at BETWEEN '2024-03-01' AND '2024-03-31'`이라면 시작 키가 있는 리프를 찾은 뒤 끝 키를 넘을 때까지 오른쪽 리프로 이동하며 읽기만 하면 된다. 같은 이유로 `ORDER BY created_at`이나 `MIN`, `MAX`도 별도의 정렬 없이 인덱스 순서를 그대로 이용할 수 있다. `LIKE 'kim%'`처럼 앞부분이 고정된 문자열 검색도 범위 검색으로 바뀌어 인덱스를 쓰지만, `LIKE '%kim'`처럼 앞에 와일드카드가 붙으면 시작 위치를 정할 수 없어 인덱스를 쓰지 못한다.

### 2.4 노드 분할과 채움률

리프 노드가 가득 찬 상태에서 새 키가 들어오면 노드를 둘로 나누고 부모에 길잡이 키를 하나 추가한다. 부모도 가득 차 있으면 분할이 위로 전파되고, 루트까지 분할되면 트리 높이가 1 늘어난다. 분할이 잦으면 쓰기 비용이 커지므로 PostgreSQL은 B-tree 인덱스를 만들 때 리프 페이지를 기본적으로 90%만 채워 두는 채움률(fillfactor) 설정을 사용한다. 갱신이 많은 테이블이라면 이 값을 70~80 정도로 낮춰 여유 공간을 더 남기기도 한다. 키가 항상 증가하는 일련번호라면 새 키가 늘 가장 오른쪽 리프에 들어가므로, 분할된 왼쪽 페이지가 거의 가득 찬 채로 남아 공간 효율이 좋다.

## 3. 해시 인덱스

### 3.1 구조와 동작

해시 인덱스는 인덱스 열의 값을 해시 함수에 넣어 나온 값으로 버킷을 정하고, 그 버킷에 행의 위치를 저장한다. 조회할 때도 같은 해시 함수로 버킷을 계산해 그 버킷 안만 살펴보면 되므로, 키의 개수와 상관없이 거의 일정한 시간에 원하는 행을 찾는다. 자료구조 수업에서 배운 메모리 해시 테이블과 원리는 같지만, 버킷이 메모리 배열의 칸이 아니라 디스크 페이지라는 점이 다르다. 한 버킷 페이지가 가득 차면 오버플로 페이지를 이어 붙이고, 전체적으로 채워진 정도가 기준을 넘으면 버킷 수를 늘린다.

PostgreSQL의 해시 인덱스는 버킷을 한꺼번에 두 배로 늘리지 않고 선형 해싱과 비슷하게 한 번에 일부 버킷만 분할해 확장한다. 1,000만 행 테이블의 인덱스를 한 번에 재배치하면 그동안 쓰기가 멈추기 때문이다. 해시 인덱스의 기본 채움률은 75로, B-tree 인덱스의 기본값 90보다 낮다. 참고로 PostgreSQL 10 이전에는 해시 인덱스 변경이 WAL에 기록되지 않아 장애 후 복구되지 않았기 때문에 사용이 권장되지 않았고, 10 버전부터 WAL 기록이 추가되면서 비로소 실무에서 고려할 수 있게 되었다. MySQL의 InnoDB 엔진은 사용자가 직접 해시 인덱스를 만드는 기능을 제공하지 않는 대신, 자주 조회되는 B+트리 페이지에 대해 메모리 안에 해시 인덱스를 자동으로 만드는 적응형 해시 인덱스를 둔다.

### 3.2 해시 인덱스를 쓸 수 없는 경우

해시 함수는 비슷한 값을 전혀 다른 버킷으로 흩어 놓도록 설계되어 있다. 그래서 해시 인덱스는 등호(`=`) 비교에만 쓸 수 있고, `<`, `>`, `BETWEEN` 같은 범위 조건이나 `ORDER BY` 정렬, `LIKE 'abc%'` 같은 접두어 검색에는 전혀 도움이 되지 않는다. 또한 PostgreSQL의 해시 인덱스는 하나의 열에만 만들 수 있고, 유일성 제약(UNIQUE)을 강제하는 데 쓸 수 없다.

실습에서 1,000만 행의 회원 테이블에 길이 40자 정도의 이메일 열로 B+트리 인덱스와 해시 인덱스를 각각 만들어 비교했다. 해시 인덱스는 이메일 문자열 대신 4바이트 해시 값만 저장하기 때문에 크기가 B+트리 인덱스의 약 60%였고, 등호 조회 속도는 둘 다 0.1밀리초 안팎으로 의미 있는 차이가 없었다. 결론적으로 긴 문자열 키를 등호로만 조회하고 인덱스 크기를 줄이고 싶을 때가 아니라면, 대부분의 경우 B+트리 인덱스를 기본으로 선택하는 것이 안전하다.

## 4. 복합 인덱스와 커버링 인덱스

### 4.1 열 순서가 중요한 이유

복합 인덱스는 여러 열을 묶어 하나의 인덱스로 만든 것이다. `(customer_id, created_at)` 순서로 만든 인덱스는 전화번호부처럼 먼저 고객 번호로 정렬하고, 같은 고객 안에서 주문 일시로 정렬한다. 따라서 `WHERE customer_id = 7 AND created_at >= '2024-01-01'`이나 `WHERE customer_id = 7` 조건에는 이 인덱스를 효율적으로 쓸 수 있지만, `WHERE created_at >= '2024-01-01'`처럼 첫 번째 열 없이 두 번째 열만 조건에 쓰면 인덱스 전체를 훑어야 한다. 이를 가장 왼쪽 접두어 규칙이라고 부른다.

열 순서를 정할 때는 등호 조건으로 쓰이는 열을 앞에, 범위 조건으로 쓰이는 열을 뒤에 두는 것이 원칙이다. 범위 조건이 걸린 열 뒤에 오는 열은 탐색 범위를 좁히는 데 쓰이지 못하기 때문이다. 흔히 "선택도가 높은 열을 앞에 두라"고 하지만, 실제로는 질의에서 어떤 조건이 함께 쓰이는지가 먼저다.

### 4.2 커버링 인덱스

질의에 필요한 모든 열이 인덱스 안에 들어 있으면, 데이터베이스는 테이블 본체를 읽지 않고 인덱스만으로 결과를 만들 수 있다. 이런 인덱스를 커버링 인덱스라고 하며, PostgreSQL 실행 계획에서는 Index Only Scan으로 표시된다. `SELECT created_at, total_price FROM orders WHERE customer_id = 7`이라면 `(customer_id, created_at) INCLUDE (total_price)` 인덱스로 테이블 접근을 없앨 수 있다. 실습에서 고객 한 명의 주문 2,000건을 조회했을 때 일반 인덱스 스캔은 약 8밀리초, 커버링 인덱스는 약 1.5밀리초가 걸렸다.

## 5. 인덱스를 설계할 때의 체크리스트

### 5.1 인덱스가 무시되는 경우

인덱스를 만들어 두었는데도 쓰이지 않는 경우가 생각보다 많다. 첫째, 인덱스 열에 함수나 연산을 적용하면 인덱스를 쓸 수 없다. `WHERE LOWER(email) = 'a@b.com'`이라면 `LOWER(email)`에 대한 함수 기반 인덱스를 따로 만들어야 한다. 둘째, 열 타입과 비교 값의 타입이 다르면 암묵적 형 변환 때문에 인덱스가 무시될 수 있다. 셋째, 조건에 맞는 행이 전체의 상당 부분이면 옵티마이저는 인덱스를 거쳐 행을 하나씩 찾는 것보다 테이블 전체를 순서대로 읽는 편이 싸다고 판단한다. 성별처럼 값의 종류가 두세 개뿐인 열에 단독 인덱스를 만드는 것이 거의 의미 없는 이유다.

### 5.2 실행 계획 확인 습관

인덱스가 실제로 쓰이는지는 추측하지 말고 `EXPLAIN ANALYZE`로 확인한다. Seq Scan은 전체 테이블 스캔, Index Scan은 인덱스로 위치를 찾은 뒤 테이블을 읽는 방식, Bitmap Heap Scan은 인덱스로 찾은 위치를 모아 페이지 순서대로 테이블을 읽는 방식이다. 실행 계획의 예상 행 수와 실제 행 수가 열 배 이상 차이 난다면 통계 정보가 오래된 것이므로 `ANALYZE`를 실행해 통계를 갱신한다. 과제로는 수업용 쇼핑몰 스키마에서 느린 질의 다섯 개를 골라 인덱스를 설계하고, 적용 전후의 실행 계획과 수행 시간을 비교해 제출한다.
